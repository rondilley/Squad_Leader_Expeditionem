## Executive Summary

The architecture is directionally sound. It reflects the major owner decisions: Python core first, local host topology, generated boards with private reference layouts, per-player views, integer LOS, legal-command generation as the shared substrate for client, trainer, and model agents, and the fourth tuned-model agent family.

The document is not yet tight enough to code from. The dominant risk is not the high-level topology. The dominant risk is the command and decision-frame seam: `ARCHITECTURE.md` uses command IDs as indexes into a legal list, sends a client hash in the sequence diagram, and expects the same list to serve replay, client intents, trainer masks, model prompts, traces, and fine-tuning. That seam will fail integration testing unless command identity, view identity, and replay serialization are made canonical.

The second load-bearing risk is LOS. The integer-lattice vector approach is the right class of solution, but the current write-up overclaims. `ARCHITECTURE.md` says the 1000 by 866 lattice approximation changes no LOS, caches unordered pairs as one byte, and handles tie breaks including the firer-choice rule. Those statements do not all fit together as written.

The third risk is the tuned-model pipeline. A 7B LoRA on one GPU from 200 games is plausible with the right GPU, context length, quantization, and tooling. A 14B run, Q8 preference, 5500-token examples, GGUF merge/export, constrained decoding, and a 24-hour bound are not realistic as a blanket architecture claim without a GPU memory target and a staged smoke path.

The defensible product is a rule-cited engine with AI consumers, replay, and audit logs. `ARCHITECTURE.md` sections 1 to 3 implement that thesis with one side-effect-free core and rule IDs in events.

## Critical Contradictions and Feasibility Problems

### CRITICAL: Client hash handling contradicts the requirements

**Sources:**

- `REQUIREMENTS.md` DR-04: “A client sends intent only and MUST NOT send a hash.”
- `ARCHITECTURE.md` section 12 sequence diagram: “C->>H: intent with command id and view hash.”
- `ARCHITECTURE.md` section 8: “A stale client cannot apply a command against a state it has not seen. The host compares the state hash the view was built from.”

**Finding:**

The architecture contradicts DR-04. The host can compare against server-side state, but the client must not send a state hash. If the client needs freshness, it should send an opaque `view_seq` or `decision_frame_id` issued by the host, not a hash of state. The hash is an integrity artifact owned by the host and replay system.

**Fix:**

Replace “view hash” with a server-issued opaque decision-frame token. The command envelope should be:

```json
{
  "room_id": "...",
  "player_slot": "A",
  "decision_frame_id": "server-issued opaque id",
  "command_id": "stable id from that frame"
}
```

The host maps `decision_frame_id` to the legal list it sent. The client never sends or computes a state hash.

### CRITICAL: Command IDs as indexes will break replay, traces, trainer masks, and model prompts

**Sources:**

- `ARCHITECTURE.md` section 3: legal-command generation is “the load-bearing design.”
- `ARCHITECTURE.md` section 8: “A command ID is an index into the legal list the host sent.”
- `REQUIREMENTS.md` DR-04: command log stores sequence number, player, phase, command ID, and hash after the command.
- `REQUIREMENTS.md` FR-60 and DR-08: traces store legal command IDs and selected command ID.
- `ARCHITECTURE.md` section 9.3: model emits JSON with a command ID enum.
- `ARCHITECTURE.md` section 9.2: trainer masks come from the legal list.

**Finding:**

An index into a transient list is not a replayable command identity. It is not stable across code changes, legal-list ordering changes, view projections, trainer batching, prompt truncation, or trace reuse. If traces hold only transient IDs, they are weak training data. If command logs hold only transient IDs, replay depends on re-generating the exact list order forever.

**Fix:**

Make a `DecisionFrame` the shared artifact across host, trainer, harness, and traces. Each frame contains:

- canonical state hash, host-owned
- active player
- phase and sub-step
- full legal command payloads
- stable command IDs derived from canonical serialization, or assigned deterministically from canonical order
- optional presentation labels for client and LLM
- masks for trainer heads

The command log must store the full canonical command payload, not only the ID. The ID is for selection. The payload is for replay.

### HIGH: LOS cache design contradicts ordered-pair requirement and underspecifies tie behavior

**Sources:**

- `REQUIREMENTS.md` FR-28: LOS cache result for each **ordered** hex pair.
- `ARCHITECTURE.md` section 5: “54,285 unordered pairs” per board and “one byte for each pair.”
- `ARCHITECTURE.md` section 5: tie breaks include rule 7.1 and rule 17.7, with rule 17.7 giving the firer a choice along a hexside.
- `SUCCESS_CRITERIA.md` TC-03 and TR-03: legal-action rejection and LOS property testing, including symmetry.

**Finding:**

The architecture says unordered cache. The requirement says ordered cache. More importantly, one byte per unordered pair is too simple if the LOS result needs context, firer choice, dynamic hindrances, or later elevation. A static unordered cache can answer “which static polygons does this segment touch.” It cannot by itself answer all rule-context LOS questions.

**Fix:**

Split LOS into two layers:

1. `StaticLosGeometryCache`: unordered or ordered, stores touched terrain polygon IDs, touched hexsides, vertex-touch flags, and possible tie alternatives.
2. `LosRuleEvaluator`: takes attacker, defender, phase, board state, smoke, fire, vehicles, elevation rules, and optional switches, then returns blocked, clear, hindrance count, and rule IDs.

If FR-28 keeps “ordered,” update the architecture. If unordered is sufficient for static geometry, change FR-28 to say static geometric pairs are unordered, but rule evaluation is contextual.

### HIGH: Reference-mode traces and tuned weights are not safe as written

**Sources:**

- `REQUIREMENTS.md` SR-10: “The trace data set and the tuned model weights MUST NOT contain reference-mode board data.”
- `ARCHITECTURE.md` section 9.4: “Traces from reference-mode games stay on the owner's machine.”
- `REQUIREMENTS.md` FR-27: reference-mode layouts are private and never shipped.
- `VISION.md` bet 5: four 1977 layouts stay private reference data.

**Finding:**

Keeping reference-mode traces on the owner’s machine is not enough. If those traces are used to fine-tune a model, the tuned weights can encode reference-mode layout facts. SR-10 forbids that. `ARCHITECTURE.md` does not say that reference-mode traces are excluded from fine-tuning or scrubbed before training.

**Fix:**

Add a hard rule: public or shareable tuned weights must be trained only on generated-mode traces. Reference-mode traces may be used for private analysis, but not for any model artifact that leaves the owner’s machine. The trace builder must tag `board_source: generated | reference_private` and the fine-tune command must reject `reference_private` unless an explicit `--private-local-only` flag is used.

## Security Findings

### HIGH: Reference-mode data can leak through model training

**Sources:** `REQUIREMENTS.md` SR-10, FR-27; `ARCHITECTURE.md` section 9.4.

The model pipeline is a new exfiltration path. It is not enough to keep reference-mode traces out of git. If reference-mode traces are used to train a LoRA adapter, the adapter can encode board layout facts. Add source tags to traces and make the fine-tune command reject private reference-mode traces by default.

### HIGH: Client-side hash language weakens the trust boundary

**Sources:** `REQUIREMENTS.md` DR-04; `ARCHITECTURE.md` section 12.

The client must not participate in state hashing. State hash is a host/core/replay integrity mechanism. Use a server-issued decision-frame token for staleness. Do not ask the browser to send a state hash.

### MEDIUM: IP and release controls are underrepresented in the architecture

**Sources:** `REQUIREMENTS.md` SR-06, SR-07, SR-08; `ARCHITECTURE.md` section 10.

`ARCHITECTURE.md` section 10 lists per-player view, provider allowlist, and key/header redaction as security controls. It does not include the GPL notice, source-link obligation, protected-brand controls, or release audit. Those are not optional. The project’s legal posture depends on them as much as the provider controls.

### MEDIUM: LAN security is accurately scoped, but origin checks should not be oversold

**Sources:** `REQUIREMENTS.md` SR-03; `ARCHITECTURE.md` section 8.

The architecture correctly says LAN play is trusted-party convenience and not confidentiality against a hostile LAN machine. Keep that language. WebSocket origin checks and room codes reduce accidental joins and browser-based misuse. They do not make LAN play secure against an active local attacker.

## Efficacy

### Rule-cited engine

The architecture will achieve the rule-audit goal if every event carries rule IDs and the conformance corpus is real. `ARCHITECTURE.md` section 3.3 and `SUCCESS_CRITERIA.md` TC-01 support this.

The weak point is rule ambiguity. `ARCHITECTURE.md` section 6 says Q and A rulings are data, but the command model must also encode optional rule switches. FR-08 is only partially reflected.

### Model agents

The harness design is directionally effective: text state, legal list, free text analysis, JSON command selection, retry, fallback. This matches `REQUIREMENTS.md` FR-45 to FR-48 and `ARCHITECTURE.md` section 9.3.

The efficacy claim for tuned models is weaker. `VISION.md` bet 3 says a tuned 7B to 14B model makes fewer invalid commands and wins more games than the prompted base. `SUCCESS_CRITERIA.md` TC-36 only measures invalid-command direction and has no quality threshold. If constrained decoding is on for both models, invalid command rate can become a grammar artifact rather than a model-skill measure.

Recommendation: make the tuned-model comparison measure:

- valid command without constraint
- valid command with constraint
- fallback rate
- win rate against the same scripted agent set
- delta against same base prompted model
- decision latency

### Learned agents

`ARCHITECTURE.md` section 9.2 reflects `VISION.md` bet 4. The staged ladder is the right risk control. Do not relax the 1 million and 10 million stop points. PPO may learn nothing useful in this game; the ladder is the only cheap way to find out.

## Integer Lattice LOS Assessment

The integer lattice LOS approach is sound in class, but not sound as currently specified.

### What is sound

- Center-to-center segment against terrain polygons matches the rule concept better than hex-cell LOS. Source: `ARCHITECTURE.md` section 5; research report section 5.3.
- Integer cross products avoid Python/Rust/WebAssembly float drift. Source: `REQUIREMENTS.md` NFR-05 and FR-28; `ARCHITECTURE.md` section 5.
- Caching static LOS work is necessary for NFR-01. Source: `REQUIREMENTS.md` NFR-01; `ARCHITECTURE.md` section 5.

### What is not sound yet

1. **The 1000 by 866 grid is an approximation, not exact geometry.**  
   `ARCHITECTURE.md` section 5 says the approximation changes no LOS because terrain polygons are coarse. That is an assertion. It must be proven by conformance cases or replaced with a rational coordinate system that does not require the claim.

2. **The cache cannot be just one byte if it must support tie and context.**  
   `ARCHITECTURE.md` section 5 says one byte holds clear, blocked, or hindrance count. But the same section says rule 17.7 gives the firer a choice for hexside LOS. A one-byte static result cannot preserve alternatives.

3. **Dynamic hindrances are not cacheable as static board data.**  
   `ARCHITECTURE.md` section 5 mentions smoke, vehicles, and fire as dynamic hindrances. The static cache can accelerate the query, but the final LOS result must be evaluated at runtime.

4. **Rendering and rules can drift.**  
   `ARCHITECTURE.md` section 7 has a polygon pass and a client style pass. If the client renders different shapes from the core polygons, the LOS thread can visually contradict the rule result. The core polygon data must be the render source of truth.

## Tuned-Model Pipeline Realism on One GPU

**Sources:**

- `REQUIREMENTS.md` FR-61, FR-62, NFR-09, IR-08.
- `ARCHITECTURE.md` section 9.4.
- `VISION.md` bet 3.
- `REQUIREMENTS.md` open question O-02 and O-06.

Judgment: **7B LoRA is plausible. 14B under the stated constraints is not a safe promise. The architecture is hand-waving until GPU memory, quantization, context length, and toolchain are fixed.**

Specific issues:

- **GPU unspecified.** `REQUIREMENTS.md` O-02 says the workstation GPU and memory are unknown. NFR-09 cannot be a serious gate until this is known.
- **Context length is expensive.** `ARCHITECTURE.md` section 9.3 uses about 5,500 input tokens. With 200 games and roughly dozens of decisions per game, the token volume can be large enough that 24 hours depends heavily on packing, epochs, sequence length, and GPU.
- **7B and 14B are materially different.** A 7B QLoRA run on a 24 GB GPU is plausible. A 14B run may require more memory, shorter context, heavier quantization, CPU offload, or much slower throughput.
- **Q8 recommendation conflicts with training practicality.** `REQUIREMENTS.md` O-06 recommends a 7B or 8B instruction model that llama-server runs in Q8. Q8 inference is not the same as LoRA training. If the training path uses 4-bit QLoRA, reconcile that with `VISION.md` bet 3, which warns that 4-bit quantization can degrade model behavior.
- **GGUF merge/export is a fragile integration point.** `ARCHITECTURE.md` section 9.4 says the merged model exports to GGUF and loads on llama-server. That may work, but it is tool-version-sensitive and should be tested as an early smoke, not assumed.
- **TC-36 can be gamed by constrained decoding.** `SUCCESS_CRITERIA.md` TC-36 compares invalid-command rate with constrained decoding on. If both models are constrained to legal IDs, invalid-command rate may be near zero for both and says little about learned game skill.

Recommendation: constrain year-one tuned work to one explicit profile:

- 7B or 8B base model
- generated-mode traces only
- fixed maximum context length
- LoRA or QLoRA profile named in the run artifact
- 50-step smoke test first
- 200-game fine-tune only after smoke export loads in llama-server
- 14B as an optional stretch, not a MUST-equivalent expectation

## Performance and Cost

The performance architecture has the right levers: LOS cache, integer math, no browser rules, legal-list reuse, and no artifact writes in the benchmark.

The weak point is when TC-09 is measured. `REQUIREMENTS.md` NFR-01 says the benchmark includes legal-command generation, observation construction, and hashing. `tasks/todo.md` slice 2 measures a movement-only game. That number is useful, but it is not the real v0.1 gate. The real gate is after slice 3, when scenario 1 includes fire, morale, rout, defensive fire, support weapons, close combat, events, and observation construction.

Cost controls for model agents are adequate at architecture level. `ARCHITECTURE.md` section 10 records cost per call. `REQUIREMENTS.md` OR-02 requires tokens, latency, cost, retry, fallback, and constrained-decoding flags.

## Integration Seam Most Likely to Fail

The most likely integration failure is the seam between:

- core legal-command generation
- host view projection
- client command selection
- trainer masks
- model-agent legal ID enum
- trace and replay serialization

**Sources:**

- `ARCHITECTURE.md` sections 3, 8, 9.2, 9.3, 9.4, and 12.
- `REQUIREMENTS.md` FR-04, FR-43, FR-50, FR-60, DR-04, DR-08.

The likely failure mode:

1. Core generates legal commands in some order.
2. Host sends indexes to the client.
3. Client sends an index back.
4. Trainer builds masks from a different command decomposition.
5. Model prompt uses IDs that are only local to the prompt.
6. Trace stores selected ID.
7. Replay later cannot reconstruct the exact same legal list order after a code or data change.

Fix this before writing code. A canonical `DecisionFrame` is the integration contract.

## Highest-Leverage Refactor

Refactor the design around a single canonical `DecisionFrame` and `StepResult`.

This simplifies the host, client, trainer, model harness, trace writer, replay tool, and tournament runner without losing capability.

### Current design problem

The same concept is described several ways:

- legal commands for the active player, `ARCHITECTURE.md` section 3
- command ID as index, section 8
- trainer composed action heads, section 9.2
- model JSON enum, section 9.3
- trace selected ID, section 9.4
- replay command log, section 12 and `REQUIREMENTS.md` DR-04

That is too many representations for the load-bearing interface.

### Refactor target

Define two core contracts:

```text
DecisionFrame:
  frame_id
  state_hash
  active_player
  phase
  sub_step
  player_view
  legal_commands:
    command_id
    canonical_command_payload
    display_label
    rule_ids
    trainer_projection

StepResult:
  accepted
  command_payload
  events
  new_state_hash
  next_decision_frame
  rejection_rule_id and message, if rejected
```

Then:

- host sends `DecisionFrame` to client
- client returns `frame_id` plus `command_id`
- trainer consumes `trainer_projection`
- model prompt consumes `display_label` and `command_id`
- trace stores view text, legal command IDs, selected ID, and canonical payload
- replay uses canonical payloads, not transient indexes

This is the one refactor that can plausibly remove 30 percent of future complexity.

## Bottom Line

This is worth building, but not from the current architecture unchanged. The system will stand or fall on canonical legal commands, deterministic replay, and LOS correctness, not on the browser shell or model providers.

Before coding, fix the command identity model, the client hash contradiction, the LOS cache semantics, and the reference-trace training leak. If implementation starts with the current document, the first serious integration test between core, host, trainer, model harness, and replay will expose the same design gaps after they are already expensive.
