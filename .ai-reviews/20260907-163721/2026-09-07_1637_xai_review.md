# Squad_Leader_AI Architecture and Project Assessment

## Executive Summary

The core idea is sound and worth building. One deterministic, side-effect-free rules core that emits rule IDs and supports replay, combined with a per-player view host and four pluggable agent families behind a single interface, directly satisfies the five strategic bets in VISION.md and the majority of MUST requirements in REQUIREMENTS.md. The first milestone (v0.1 headless rules proof) is the right size and sequence.

The dominant issues are three. First, ARCHITECTURE.md does not address every MUST: FR-09 (concealment), FR-42 (per-player views on every outbound artifact), FR-60 (trace data set from the acting agent's view only), and FR-62 (constrained decoding on the tuned model) receive only high-level treatment or none at all. Second, the tuned-model pipeline in section 9.4 is the largest unproven seam; it assumes 200 games of traces will produce a measurable improvement over the prompted baseline on one GPU, yet supplies no data-volume model, no overfitting control, and no fallback if the fine-tune degrades. Third, the command model in section 3.1 is incomplete for rules 1-21: it defines fire-group and rout commands but omits the exact sub-step transitions for Prep Fire and Defensive Fire that the "Advanced Sequence of Play" on page 41 requires.

The load-bearing dependency is the legal-command list generator inside the core; everything else (trainer mask, model harness, client click targets, replay validation) depends on it. It sits on the critical path and is correctly placed in v0.1. The seam most likely to fail integration testing is the boundary between host view generation and the three non-browser consumers (trainer, harness, trace writer), because the trainer must use the same view function yet the document never states how the view function is made cheap enough for millions of headless steps.

A hostile reviewer would call section 9.4 hand-waving and would also flag the absence of any concrete state-machine table that maps every sub-step on page 41 to a command window or automatic transition. The highest-leverage refactor that removes roughly 30 percent of the moving parts without loss of capability is to collapse the four agent families into a single harness that owns the text view, the JSON schema, the retry loop, and the constrained-decoding grammar; the four "families" then become only different observation sources and different model loaders. This removes the duplicated harness logic that currently appears in sections 9.3 and 9.4.

## What Validates Well

The integer lattice LOS design in section 5 is sound. It matches the thread rule in 7.1, reproduces the VASL pixel-walk result with less data, stays inside the integer-arithmetic mandate of NFR-05, and supplies the cache that is the single largest lever on NFR-01. The decision to keep the four 1977 layouts private and ship only the generator plus reference-mode loader on the owner's machine satisfies both the legal analysis in RV-4 and the owner directive recorded in the consolidated review.

The command-plus-hash replay model, the seeded xoshiro128** generator, and the single conformance corpus that every binding must pass are the correct mechanisms for determinism and for the Rust port boundary in AR-05.

## Scope and Sequencing

The tiering (v0.1 to v0.4 plus RC) is correctly sized. The only cut that would materially reduce first-milestone risk without losing capability is to defer the tuned-model pipeline (FR-61, FR-62, TC-36, TC-37) to v0.5. That removes the largest unproven dependency from the 3,500 steps/s gate measurement and from the first long training run.

Proposed adjusted tiers for the next document revision:

- v0.1: headless rules 1-21, conformance corpus, throughput number, one scripted agent, run artifacts.
- v0.2: browser hot seat, reference loader, zone resolution prototype.
- v0.3: rules 22-27, scenarios 2 and 3A, LAN, per-player views, three scripted agents, trace writer.
- v0.4: PettingZoo environment, PPO ladder, prompted harness (local + one SaaS), four-family tournament without the tuned model.
- v0.5: tuned-model pipeline, constrained decoding, self-play RL on the language model if TC-36 shows gain.

## Critical Path and Leverage

The load-bearing component is the legal-command list builder inside the core. It is correctly sequenced first. The next-highest-leverage item that is not yet on the critical path is the single harness abstraction proposed above; moving it into v0.1 would collapse duplicated code and reduce the integration surface between harness and tuned model by half.

## Critical Contradictions and Feasibility Problems

No hard contradictions exist that make the design impossible. Two medium-severity gaps do exist.

- REQUIREMENTS.md FR-09 and FR-42 require concealment and per-player views on every outbound artifact by v0.3. ARCHITECTURE.md section 4 describes the view function but never states how the trainer (which must call the same function millions of times) avoids the cost when nothing is concealed. This is a performance seam, not a correctness contradiction.
- VISION.md bet 3 claims the tuned model will beat the prompted baseline. ARCHITECTURE.md 9.4 supplies no quantitative model for trace volume versus improvement and no plan if the fine-tune overfits to the scripted agents that generated most of the traces. This is a feasibility gap, not a contradiction.

## Security Findings

The threat model in REQUIREMENTS.md section 3 is carried through correctly in ARCHITECTURE.md sections 4, 8, and 10. The per-player view, the provider allow-list, and the redaction of hidden state from traces and logs are the three controls that survive compromise of any single consumer. No additional controls are required for year one.

## Efficacy

The design will deliver rule fidelity and replay correctness. It will deliver the four play modes. It is likely to deliver a usable prompted model agent once the retry-and-default harness is implemented. It is uncertain whether the tuned model will show a measurable win-rate gain over the prompted baseline on the data volume that can be collected in year one. That uncertainty is acceptable provided the comparison (TC-36) is treated as a measurement rather than a success gate.

## Performance and Cost

The single largest lever on NFR-01 is the LOS cache described in section 5. The second lever is the decision to build the legal-command list once per state and reuse it until the next command. Both are present and correctly placed.

## Acceptance Criteria and Gates

The gates in SUCCESS_CRITERIA.md are well-formed and measurable. The single change needed is to make TC-36 and TC-37 conditional on the tuned-model slice being in scope; otherwise a v0.4 release could be blocked by an experiment whose result is allowed to be "no improvement."

## Design Risks That Need Better Framing

The largest unstated risk is that the zone predicates in FR-21 may produce boards that scenario 1 cannot use. The document correctly flags this as O-04 but does not state the fallback: if zone resolution fails, generated mode is disabled for scenario 1 and only reference mode is offered until the generator is improved.

## Recommendations by Priority

P0 (fix before any code is written):

- Add an explicit state-machine table in ARCHITECTURE.md section 3.2 that maps every numbered sub-step on page 41 to either an automatic transition or a command window. Cite the rule that governs each transition.
- Move the tuned-model pipeline to v0.5 and remove its requirements from the v0.4 gates.
- State in section 4 exactly how the view function is made cheap for the trainer when no concealment is present.

P1 (before v0.2):

- Define the single harness interface that owns text view construction, schema validation, retry, and constrained decoding. Make the four families only different observation sources and loaders.
- Add a quantitative trace-volume model and an overfitting control (source-family weighting or scripted-agent trace removal) to section 9.4.

P2 (before RC):

- Write the four architecture decision records listed in appendix A.

## Documentation and Process Improvements

Create a single traceability matrix (one table, one row per FR/NFR/SR ID) that lists the exact section in ARCHITECTURE.md that satisfies it. Update it on every document revision. Add a "view cost model" subsection to section 4 that gives the big-O cost of a view when zero, one, or all units are concealed.

## Bottom Line

The architecture is worth building. The core, the command model, and the per-player view are the three pieces that must be correct first; once they exist the rest of the system is assembly. The single change that removes the largest remaining risk is to treat the tuned-model pipeline as a year-one experiment rather than a year-one deliverable and to publish the comparison result rather than gate the release on it. If that change is made, the current material is a solid foundation for slice 1.
