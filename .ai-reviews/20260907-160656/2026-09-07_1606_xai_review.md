## Executive Summary

The core idea is sound and worth building: a single deterministic rules core that supplies rule fidelity, audit logs, replay, and all four play modes while enabling both learned agents and model agents. The research synthesis in `2026-09-07_Squad_Leader_Digital_Edition_Research.md` supplies traceable evidence for every major design choice.

The first milestone is not the right size. REQUIREMENTS.md and SUCCESS_CRITERIA.md together describe a v0.9 that includes a full rules engine for sections 1-27, three scenarios, generated boards that must pass an owner taste test, three agent families, LAN play, and a measured 3,500 steps/s Python throughput gate. That scope exceeds what a solo developer can deliver in one year while also satisfying the owner decisions on Python-first, generator-only boards, and private 1977 layouts.

Dominant risks are feasibility of the throughput gate in pure Python, contradiction between the generator mandate and the requirement that boards "look like the board game," and incomplete coverage of the original ask (browser game with learning, evolution, local and SaaS models) under the stated constraints. The plan is coherent and measurable where it exists, but the critical path is mis-sequenced and several load-bearing components lack explicit derisking steps.

## What Validates Well

The traceability matrix in REQUIREMENTS.md Appendix A and the explicit requirement IDs in every FR/NFR/SR entry create a single source of truth that future sessions can follow without re-derivation. SUCCESS_CRITERIA.md section 4 correctly identifies the anti-pattern of stub-based completion claims and enforces real external service calls. The five strategic bets in VISION.md are stated plainly with failure modes and mitigations. The legal analysis in research section 6 is precise about what may and may not be shipped.

## Scope and Sequencing

The current v0.1 description is a release candidate wearing a milestone label. Cut the following from first delivery:

- Model agent harness and all SaaS/local provider adapters (move to v0.2).
- Snapshot league and PPO training run (move to v0.2 after the throughput gate is proven).
- LAN play and room-code host (move to v0.2).
- Generated boards required to satisfy the full look rubric (keep only the generator format and one city-type prototype; the rubric test becomes a v0.2 gate).

Proposed tiers:

- v0.1: Python core for rules 1-27, scenarios 1-3 from data files, hot-seat browser client only, three scripted agents, conformance battery, determinism tests, throughput measurement. No training, no model agents, no LAN.
- v0.2: Add model agent harness, local model integration, first 100-million-step PPO run if gate passed, LAN host, look-rubric scoring session.
- Release candidate: Full agent families, all 12 scenarios on private layouts, unattended league, public title and GPL-3 release.

## Critical Path and Leverage

The load-bearing component is the rules core itself (AR-01, FR-01-FR-17). Everything else depends on it producing correct legal-action masks, rule-cited logs, and deterministic replay. The plan does not derisk the core first; instead it interleaves board generation, browser rendering, agent harnesses, and the throughput measurement. The correct sequence is: core + conformance battery + determinism tests, then hot-seat client, then throughput measurement, then everything else.

## Critical Contradictions and Feasibility Problems

CRITICAL: AR-05 and NFR-01 require a pure Python core to deliver 3,500 steps/s end-to-end before any Rust port. RV-5 section 5 states that 1,000-5,000 steps/s per core is possible only if observation construction is cheap; no measurement or prototype exists yet. If the gate fails, the Rust port must occur before training, yet the owner decision locks Python first. This is a direct contradiction between the throughput claim and the language choice.

HIGH: FR-25, FR-30, and owner decision on private layouts require the generator to produce boards that "look like the board game" while the four 1977 layouts remain private and are never shipped. TC-14 makes the owner taste test the acceptance gate. No written rubric exists at review time (O-04), and no prototype has been scored. The two statements cannot both be true without additional work that is not scoped.

MEDIUM: The original ask requires "learning and evolution" plus local and SaaS models in the browser game. REQUIREMENTS.md moves the model harness and PPO run to v0.2 or later; VISION.md section 5.1 still lists them as year-one deliverables. The documents disagree on what ships in the first milestone.

## Security Findings

The key-file pattern (SR-01, SR-02) and GPL-3 section 7 notice (SR-06) are correctly specified. The LAN trust model (SR-03) is explicit and limited. No findings that contradict the stated posture.

## Efficacy

The engine-verified model agent harness (FR-45-FR-48) correctly absorbs the failure modes reported in BALROG and WARBENCH. The legal-action mask and retry-then-default design is sound. The PPO unit-by-unit action with mask follows published Gym-uRTS precedent. No efficacy gap in the AI approach itself; the gap is in milestone sequencing.

## Performance and Cost

NFR-01 is the only load-bearing performance claim. The 3,500 steps/s figure is derived from 100-300 million steps in 24 hours; no prototype measurement supports it for a Squad Leader observation that includes concealment, LOS, and morale state. The cost model in RV-6 section 7 is accurate for the model-agent path but is not part of v0.1 under the recommended cut.

## Acceptance Criteria and Gates

SUCCESS_CRITERIA.md is the strongest document. Every criterion names its test, data source, and threshold. The anti-pattern clause in section 4 is correctly binding. The only weakness is that TC-14 depends on a rubric that does not yet exist in the reviewed material.

## Design Risks That Need Better Framing

The decision to keep the four 1977 layouts private while still claiming "boards and counters that look like the 1977 game" is under-specified. The generator must either pass the taste test on its own or the scenarios must run exclusively on private reference data; the documents do not state which outcome is acceptable for v0.1.

## Recommendations by Priority

P0 (fix before coding): Resolve the throughput contradiction. Either measure a Python prototype against NFR-01 on the actual workstation or change AR-05 to allow a Rust core from the start. Record the decision in an ADR.

P1: Write the look rubric (O-04) and run a scored prototype of the generator before committing to board generation as a v0.1 deliverable.

P2: Align VISION.md section 5.1 with the scoped v0.1 in REQUIREMENTS.md so that model agents and training are explicitly year-two work.

P3: Add an explicit milestone for "core + hot seat only" that can be completed in 3-4 months.

## Documentation and Process Improvements

Create a single `ARCHITECTURE.md` that cross-references the requirement IDs instead of leaving the design distributed across VISION, REQUIREMENTS, and the research synthesis. Add a traceability matrix that maps each open question (OQ-R1 through OQ-R7 and O-01 through O-05) to the document section that will close it. Update `tasks/lessons.md` after every owner decision that changes scope.

## Bottom Line

The concept is worth building and the documentation is unusually coherent and measurable. The current first milestone cannot be delivered by one developer under the stated constraints. Cut model agents, training, and LAN from v0.1, resolve the Python throughput gate with a measurement or a language change, and write the board look rubric before any generator work begins. Without those three changes the project will discover the contradictions during implementation rather than before coding starts.
