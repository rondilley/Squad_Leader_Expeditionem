# Squad_Leader_AI Architecture and Project Assessment

- Repository state: documentation-only, no implementation code

## Executive Summary

**Verdict: conditionally worth building as a private, base-game rules-engine project. It is not ready for broad implementation.** The defensible core is a deterministic, auditable Game Set I engine with generated boards, new art, scripted opponents, replay, and a browser client. The engine, not the LLM layer or browser rendering, is the product.

The first milestone is the wrong size. It is described as an MVP, but it combines a 27-rule tactical rules engine, three scenarios, a board generator, counter rendering, hot seat, LAN multiplayer, three scripted agents, five SaaS adapters, local-model support, PPO training, a self-play league, deterministic replay, cross-platform determinism, and a 24-hour reliability requirement. This is several milestones, not one.

The dominant issue is an architecture contradiction: the project requires a **Python-only core for MVP** while also requiring **offline browser hot-seat play with no browser rule logic**. That cannot work as written. A Python core cannot execute in a normal browser without a Python runtime/binding, and the stated architecture allows the browser either to use a compiled WebAssembly core or an authoritative host. The core is explicitly Python until the throughput gate fails. Therefore, offline browser hot seat cannot be delivered under the current MVP architecture.

The second load-bearing risk is rules fidelity. The project’s stated differentiator is audited correctness, but it has no authoritative, versioned, reviewed rule-data corpus in the repository, no included Q-and-A corpus, no complete conformance-case design, and no adequate validation threshold. One conformance case per rule ID will not establish correctness for rules such as movement, LOS, fire groups, concealment, rout, close combat, and sewers.

The third risk is legal and product coherence. The plan correctly excludes shipped scans, original art, and original board layouts. But it still promises that scenarios 1 to 3 “play” while the public build cannot ship the historical map layouts that make those scenarios their intended scenarios. It can ship scenario-inspired rules/data operating on generated boards, or it can run the original scenarios only on the owner’s unshipped local reference data. These are different products and need separate naming and acceptance criteria.

## What Validates Well

1. **The project correctly identifies the engine as the shared asset.**  
   `docs/VISION.md`, section 2 and bet 2, and `docs/REQUIREMENTS.md`, AR-01 through AR-04, correctly require one deterministic core for browser, LAN host, training, agents, and replay. This is the one architectural decision that prevents immediate rule drift.

2. **Deterministic command replay is the correct foundation.**  
   `docs/REQUIREMENTS.md`, FR-11 through FR-13, DR-04, and NFR-04 require a core-owned seeded generator, ordered commands, state hashes, and replay verification. This is necessary for debugging rules, tournament reproducibility, regression testing, and RL artifacts.

3. **The AI is correctly subordinate to engine legality.**  
   `docs/REQUIREMENTS.md`, FR-43 through FR-48 and SR-04, correctly define agents as choosing from engine-produced legal actions. This makes LLM invalidity survivable and avoids treating model prose as executable authority.

4. **The plan recognizes that local and SaaS model agents are not reliable rules engines.**  
   `docs/2026-09-07_Squad_Leader_Digital_Edition_Research.md`, sections 8 and 11, explicitly records invalid action rates, fallback behavior, latency, cost, and the need for an engine-verified fallback. That is materially more realistic than claiming LLMs can independently play a rules-dense wargame.

5. **The plan correctly cuts armor from the first rules milestone.**  
   `docs/2026-09-07_Squad_Leader_Digital_Edition_Research.md`, sections 3.2, 11.1, and OQ-R1, and `docs/REQUIREMENTS.md`, FR-16, recognize that armor cannot be implemented correctly until missing reference-table data is sourced. This is sound scope discipline.

6. **Generated boards and original art are the right direction under the owner’s legal constraints.**  
   The owner’s decision, reflected in `docs/VISION.md`, bet 5, and `docs/REQUIREMENTS.md`, SR-07 and SR-08, avoids knowingly shipping scans, source board art, or original layout data. That reduces obvious infringement exposure, although it does not eliminate legal review needs.

## Scope and Sequencing

The stated MVP is a v0.9 program wearing an MVP label. It has at least five independent hard projects:

1. Correctly implement the Game Set I rules.
2. Deliver a usable browser tabletop.
3. Implement secrecy-preserving hot seat and LAN play.
4. Build a high-throughput RL environment and PPO training system.
5. Build and operate local plus five SaaS LLM adapters.

A solo developer should not build these in parallel. They share an engine, but they do not share validation work.

### Recommended phased milestones

### v0.1: Headless Game Set I rules proof

Ship only:

- One Python core.
- Scenario 1 only.
- One generated, non-historical city-board fixture.
- New counter data and minimal text rendering. No final visual style work.
- Rules necessary for Scenario 1 only, with explicitly enumerated rule IDs and subrules.
- Deterministic command log, state hash, action log, and replay.
- One scripted opponent.
- Headless computer-versus-computer execution.
- Rule conformance tests based on independently derived expected outcomes.
- A measured throughput baseline on the actual workstation.

Do not ship yet:

- Browser UI.
- LAN.
- Scenario 2, scenario 3, or 3A.
- Board generator types beyond the single board fixture needed for Scenario 1.
- PPO.
- League play.
- LLM agents.
- SaaS adapters.
- SQLite indexing.
- Five-provider failover.
- Final counter art and 1977-style rendering.

**Exit gate:** 100 deterministic Scenario 1 headless games complete without crashes, replay hashes match, and rule tests cover every implemented rule branch. This milestone answers the only question that matters first: can the engine faithfully execute a bounded game?

### v0.2: Browser hot seat and visual proof

Ship:

- Browser presentation layer.
- Hot-seat play backed by the Python authoritative host.
- Pan, zoom, hex targeting, action log, and visible rule results.
- One original generated city board.
- Minimal board-generation pipeline sufficient to reproduce deterministic test boards.
- Two human play through Scenario 1 rules on a non-historical board.
- Secrecy projection for concealment, even though physically shared hot seat cannot prevent the local user from inspecting browser state.

Do not ship yet:

- Offline, no-server browser hot seat.
- LAN.
- PPO.
- LLM agents.
- Other scenarios.
- Full four-type board generator.
- Private-layout support in public test runs.

**Exit gate:** the owner completes Scenario 1 in browser hot seat and can audit every consequential resolution from the action log.

### v0.3: Scenario and multiplayer expansion

Ship:

- Scenarios 2, 3, and 3A only after their rule subsets and scenario data are independently validated.
- LAN host with two separate player-state projections.
- Session-only room-code authentication with rate limiting and connection throttling.
- Three scripted opponents.
- Tournament runner and run artifacts.

Do not ship yet:

- LLM provider fleet.
- PPO and self-play league.
- “Looks like 1977” final-art claim.
- Four board types if this delays actual rules fidelity.

**Exit gate:** two-browser LAN game completes Scenario 1 and Scenario 2 with no information disclosure between players.

### v0.4: AI research milestone

Ship:

- PettingZoo-compatible headless environment.
- Throughput measurement with a precise definition of “environment step.”
- PPO smoke training.
- One scripted baseline.
- One learned-policy evaluation protocol.
- One local-model adapter, not five SaaS providers.
- Model-agent metrics: invalid-selection rate, fallback rate, latency, tokens, cost, and win rate.

**Exit gate:** either:
- Python meets the defined throughput gate and a 10 million-step pilot gives meaningful learning evidence, or
- the project stops and ports the core before committing to 100 million steps.

A 100 million-step run should not be the first evidence that the representation, reward, action decomposition, and policy architecture can learn.

### Release candidate

Only after prior gates:

- Final original art.
- Four generated board archetypes.
- LAN hardening.
- One SaaS provider, selected deliberately.
- License and content audit.
- Public-title decision.
- Public-release decision.

## Critical Path and Leverage

The critical path is:

1. **Rule corpus and adjudication policy.**
2. **Pure deterministic state machine and legality generation.**
3. **Conformance corpus with independently expected outcomes.**
4. **State projection for hidden information.**
5. **Only then, browser, LAN, training, and models.**

The engine cannot be treated as a generic implementation exercise. The hard part is turning ambiguous and interacting tabletop procedures into deterministic legal-action generation. The project needs explicit answers to questions such as:

- What is one engine “action” during movement, fire-group declaration, rout, and close combat?
- Which decisions are atomic commands versus derived resolution events?
- How is a player allowed to inspect LOS, and how is that inspection represented in the command model?
- When players select multiple units for a fire group, what state transitions occur before dice are rolled?
- What is visible to each player at every phase and subphase?
- How are optional rules selected, persisted, logged, and included in replay hashes?
- Which official Q-and-A ruling wins when a rulebook interpretation and a Q-and-A interpretation differ?

`docs/REQUIREMENTS.md`, FR-04, assumes “the full list of legal actions for the active player in the current phase” is available. That is a major design decision, not a routine API. For a game with composed actions, fire groups, movement points, target selection, concealment, and optional procedural choices, legal-action enumeration can become the dominant engine and RL cost.

The plan should derisk legal-action representation before rendering or provider integration. A thin vertical slice of Scenario 1 with one rally, movement, defensive fire, rout, and close-combat path is more valuable than building all integrations.

## Critical Contradictions and Feasibility Problems

### CRITICAL: Python-first core conflicts with serverless browser hot seat

**Sources:**

- `docs/REQUIREMENTS.md`, AR-05: “The core language is Python for the MVP.”
- `docs/REQUIREMENTS.md`, AR-06: the browser gets rule results through a compiled-to-WebAssembly binding or authoritative host.
- `docs/REQUIREMENTS.md`, FR-36: “The client MUST run without a server for hot seat play.”
- `docs/VISION.md`, bet 2: a Rust port happens only if the Python performance gate fails.
- Research report, section 9.1: WebAssembly sharing is presented as a Rust-core approach, not a Python-core approach.

**Finding:** These requirements cannot all be true as written. A standard browser cannot directly run a Python rules core. If the browser has no rules logic, it requires an authoritative host. If hot seat must run without a server, it requires a browser-executable rules core, such as Rust/Wasm, or an explicitly adopted browser Python runtime. Neither is the selected MVP architecture.

**Required resolution:** Choose one:

1. **Recommended:** Define v0.2 hot seat as local-hosted hot seat. The browser is a client, and the owner runs a local Python host process. Remove FR-36 from MVP.
2. Use Rust/Wasm from the beginning. This conflicts with the fixed Python-first owner decision.
3. Adopt Pyodide or another Python-in-browser runtime and define its packaging, determinism, performance, and testing model. This is a new architecture, not documented or validated.

### HIGH: “Scenarios 1 to 3 play” is incompatible with not shipping their boards

**Sources:**

- `docs/REQUIREMENTS.md`, FR-19: scenarios 1, 2, and 3 with 3A “MUST play from data files.”
- `docs/REQUIREMENTS.md`, FR-27: private reference layouts are loaded locally so all printed scenarios can play on the owner’s machine.
- `docs/REQUIREMENTS.md`, SR-07: the project must not commit or ship layouts transcribed from the four 1977 boards.
- `docs/VISION.md`, bet 5: the original layouts remain private reference data.
- Research report, section 4.3: the original scenario cards define board configuration and historical setup.

**Finding:** A scenario is not just a force list and victory condition. The original scenarios are coupled to particular board layouts, terrain, roads, buildings, elevations, and setup areas. A generated board satisfying geomorphic edge constraints is not the original scenario board.

The project can support two distinct modes:

- **Private reference scenario mode:** original scenario data with locally supplied private boards.
- **Public generated scenario mode:** scenario-inspired or remixed scenarios on generated boards.

It should not describe both as the same public “Scenario 1” product. Doing so creates an untestable fidelity claim and invites accidental distribution of protected layout data through fixtures, screenshots, replays, test assets, or generated output seeded to reconstruct a board.

### HIGH: The MVP scope conflicts with the stated solo-developer constraint

**Sources:**

- `docs/REQUIREMENTS.md`, MVP scope tags across FR-01 through FR-58, NFR-01 through NFR-08, SR-01 through SR-08, IR-01 through IR-07, and TR-01 through TR-10.
- `docs/VISION.md`, section 5.1, year-one end state.
- Operator note: one solo developer, one Windows 11 workstation, one NVIDIA GPU.

**Finding:** The planned MVP includes not merely all original requested play modes, but also cross-platform deterministic replay, browser performance, LAN integration, five SaaS providers, a local model endpoint, provider failover, PPO, a league, TensorBoard, SQLite indexing, visual generation, legal audits, and 24-hour unattended operation. A solo developer cannot responsibly validate all of this while also implementing Game Set I fidelity in a year without accepting shallow validation somewhere. The likely casualty will be the rules engine, which is the one component that cannot be shallow.

**Sources:**

- Research report, section 4.3: “Scenarios 1 to 3 use board 1 only and rules 1 to 41.”
- Research report, section 11.1: Game Set I first, scenarios 1 to 3, “rules 1 to 27.”
- `docs/REQUIREMENTS.md`, FR-01: rules 1 to 27.
- `docs/REQUIREMENTS.md`, FR-19: scenarios 1, 2, 3, and 3A are MVP.

If the intended scope is base versions of scenarios 1 to 3, excluding armor variation 3B, say that precisely and remove the “rules 1 to 41” statement or correct it with a rule-by-scenario matrix.

### HIGH: GPL claims are legally inaccurate

**Sources:**

- Research report, section 6.3: “GPL-3 adds one duty for served JavaScript: Corresponding Source must be available.”
- `docs/REQUIREMENTS.md`, SR-06: requires “the FSF GPL-3 section 7 notice and a link to the Corresponding Source.”
- `LICENSE`, GPL-3 sections 0, 5, 6, and 13.

**Finding:** GPL-3 does not create an Affero-style network-source-disclosure obligation merely because JavaScript is served over a network. GPL obligations concerning Corresponding Source arise when conveying object code. Network interaction without transfer is explicitly addressed in GPL-3 section 0 as not conveying. GPL-3 section 13 allows combination with AGPL-3 and does not itself add a general network-source requirement.

A served browser bundle may be conveyed, so providing corresponding source is prudent and normally required when distributing the GPL-covered bundle. But the stated legal mechanism and “section 7 notice” rationale are wrong. This should be corrected before it becomes a release-control requirement.

## Security Findings

### HIGH: Hidden-information requirements lack a player-view architecture

**Sources:**

- `docs/REQUIREMENTS.md`, FR-09, FR-10, FR-42.
- `docs/REQUIREMENTS.md`, FR-38: LAN play through an authoritative host.
- `docs/REQUIREMENTS.md`, AR-06: browser receives rule results via binding or host.
- `docs/REQUIREMENTS.md`, SR-03: room code is the only credential.

**Finding:** The engine may maintain concealment and hidden placement internally, but that does not protect secrecy if a browser receives the complete game state. The architecture must require a **per-player state projection**, separate from authoritative state, for every outbound command, game snapshot, replay viewer, log entry, model prompt, and browser debug channel.

A client that receives concealed units and merely hides them in CSS, a canvas layer, or JavaScript state is not protected. A user can inspect browser memory, network messages, or source maps.

**Required control:** Define:

- authoritative full state,
- player A view,
- player B view,
- spectator view, if ever supported,
- public replay view,
- owner-only private replay view.

Each must be generated server-side or by a trusted local process. The browser must only receive its authorized view.

### HIGH: A room code is not meaningful LAN authentication without transport and abuse controls

**Sources:**

- `docs/REQUIREMENTS.md`, FR-38 and SR-03.
- `docs/SUCCESS_CRITERIA.md`, TC-27 tests one rejected connection without the room code.

**Finding:** On a shared LAN, a room code sent over plain WebSocket can be sniffed and replayed. It also provides no meaningful resistance to brute force unless it has sufficient entropy and rate limits. “Trusted LAN” narrows the threat model, but the room-code requirement otherwise implies an access control property the design does not provide.

**Required control:** Either explicitly state that LAN play has no confidentiality or adversarial-LAN protection, or require:

- high-entropy room secrets, at least 128 bits,
- `wss://` or an explicit local certificate/bootstrap procedure,
- per-IP and per-room attempt limits,
- session tokens after joining,
- command sequence validation and replay rejection,
- host-side player-slot assignment,
- origin checking for WebSocket browser clients.

For a private one-workstation project, the simpler and more honest choice is to define LAN play as trusted-party convenience, not secure multiplayer.

### MEDIUM: Provider host allowlisting is underspecified

**Sources:**

- `docs/REQUIREMENTS.md`, SR-05: requests only to configured provider hosts.
- `docs/REQUIREMENTS.md`, IR-01: configurable OpenAI-compatible `http://host:port/v1` local endpoint.
- `tasks/discovery_notes.md`, section 7: same client path serves llama.cpp, Ollama, vLLM, and LM Studio.

**Finding:** A configurable URL is an SSRF boundary if any future UI, config import, scenario, prompt, or LAN participant can influence it. “Configured provider hosts” needs a definition: approved schemes, canonical host matching after redirects, private-host exceptions only for an explicit local endpoint, and no user-controlled arbitrary URLs.

This is not currently an exposed vulnerability because no implementation is present. It is an unaddressed requirement risk.

### MEDIUM: Model prompts and logs can leak private game state and keys

**Sources:**

- `docs/REQUIREMENTS.md`, FR-45 through FR-49 and OR-02.
- `docs/REQUIREMENTS.md`, FR-42.
- `docs/REQUIREMENTS.md`, DR-07: player names are session-only.
- `.gitignore`: `runs/`, logs, and `.env` files are excluded.

**Finding:** The model-agent design sends detailed game state to external SaaS providers and persists model telemetry. In a concealed-information game, the prompt must be constructed from the acting agent’s authorized view, not the full authoritative state. Logs must not contain API keys, Authorization headers, raw provider request headers, or opponent-hidden state in publicly shared run artifacts.

The requirements mention text-only model input but do not require view-safe prompt generation or log redaction.

### LOW: Key-file practice is acceptable for local development, but it needs operational boundaries

**Sources:**

- `.gitignore`, first line `*.key.txt`.
- `docs/REQUIREMENTS.md`, SR-01 and SR-02.
- `tasks/discovery_notes.md`, section 3 says five key files exist at project root.

**Finding:** The ignore rule and root-relative lookup are better than current-directory lookup. However, root key files remain exposed to local malware, backups, screenshots, and accidental archive creation. This is acceptable for a private workstation if the threat model says so. It is not a deployment strategy for any public or shared host.

## Efficacy

### Rules fidelity

The project’s main claim is that the engine will be faithful and auditable. The current criteria do not establish that claim.

`docs/SUCCESS_CRITERIA.md`, TC-01 requires one case per rule in scope. That is inadequate. Rules 1 through 27 include interactions across:

- movement and portage,
- stacking,
- LOS,
- fire-group construction,
- range and firepower modifiers,
- terrain modifiers,
- morale,
- rout,
- rally,
- leadership,
- defensive fire,
- machine-gun penetration,
- breakdown and repair,
- close combat,
- flamethrowers,
- demolition charges,
- smoke,
- concealment,
- fanaticism,
- sewer movement.

A single test per rule number can pass while nearly every interaction is wrong. For example, a test for concealment alone does not validate concealment plus area fire plus LOS plus defensive fire plus terrain plus a fire group.

**Required change:** Replace “one case per rule” with a conformance matrix:

| Rule family | Required case types |
|---|---|
| Legal action generation | valid action, invalid action, boundary action, action unavailable due to phase/history |
| Movement | each terrain, portage, stacking, leader bonus, movement interruption, defensive-fire exposure |
| LOS | clear, blocked, grazing, building, woods, wall/hedge, blind-hex and elevation cases when in scope |
| Fire | each modifier, modifier combinations, fire-group legality, weapon restrictions, dice outcomes |
| Morale/rout/rally | pass, break, elimination, legal rout choices, no legal rout, leader effects |
| Concealment | placement, loss, dummy stack, area fire, visibility to each player |
| Replay | deterministic commands, rejected commands, optional-rule selection, cross-platform hashes |

### Learning and evolution

The plan does not yet demonstrate that PPO is likely to learn useful Squad Leader tactics on the stated budget. `docs/VISION.md`, bet 4, admits this directly. The evidence supports toy-scale hex-counter learning and other RTS-like environments, not this game’s action structure or partial information.

The current 100 million-step threshold is a production-scale bet before representation viability is proved. `docs/SUCCESS_CRITERIA.md`, TC-18 only asks that the learned agent beat the weakest scripted agent over 200 games after 100 million steps. That can be gamed by a weak baseline and does not establish useful tactical play.

**Required change:**

- Add a 1 million-step learning sanity gate.
- Add a 10 million-step pilot gate.
- Freeze scripted-bot versions and publish their policies/configurations in run artifacts.
- Require confidence intervals, side balancing, fixed seed suites, and scenario stratification.
- Measure not only win rate but illegal-action attempts, game length, resignation/stall behavior, action diversity, and rule-path coverage.
- Establish a meaningful non-learning baseline before training, such as a greedy tactical bot with documented heuristics.

### Local and SaaS models

The original ask included local and SaaS models. The plan covers them, but the first milestone should not implement all five SaaS providers.

`docs/REQUIREMENTS.md`, IR-02 requires Anthropic, OpenAI, Gemini, xAI, and Mistral for MVP. That is integration breadth without evidence that model play is valuable. The actual product question is whether one local model and one SaaS model can make legal, timely, tactically nontrivial choices through the harness.

**Recommendation:** ship one local OpenAI-compatible endpoint and one SaaS provider. Add providers only when the provider abstraction has real, demonstrated cross-provider differences worth supporting.

## Performance and Cost

### The 3,500 steps/s gate is not yet measurable enough

**Sources:**

- `docs/REQUIREMENTS.md`, NFR-01.
- `docs/SUCCESS_CRITERIA.md`, TC-09.
- Research report, section 7.3.

The term “environment step” is undefined. It could mean:

- one complete engine command,
- one unit action,
- one agent decision,
- one phase completion,
- one full player turn,
- one PettingZoo `step`,
- one vectorized environment transition.

These are not interchangeable. The training design uses unit-by-unit composed actions and an end-phase action, so decisions per game vary materially based on legal choices and agent behavior. A throughput number without a frozen benchmark scenario mix, fixed seeds, fixed action-selection method, worker count, observation shape, and hardware manifest is not a gate.

**Required benchmark specification:**

- exact CPU model, core count, RAM, GPU model, driver, Python version, and OS build;
- worker counts tested separately, not merged into a range;
- scenarios and generated-board seeds;
- policy used to generate actions;
- whether action enumeration, masking, observation construction, serialization, logging, and artifact writes are included;
- median, p95, and sustained 10-minute rate;
- games/second and decisions/second, both reported;
- memory use and worker failures;
- a fixed benchmark corpus so future Python and Rust results are comparable.

### NFR-03 does not logically prove NFR-01

`docs/REQUIREMENTS.md`, NFR-03 requires a full scripted game in under two seconds on one core. NFR-01 requires 3,500 environment steps per second with 8 to 16 workers. These are related but not equivalent. A game’s action count ranges from 1,000 to 4,000 decisions according to the research. A two-second single-core game could be 500 to 2,000 steps/s, while multiprocessing overhead can reduce rather than multiply throughput on Windows.

Treat NFR-03 as a UI and regression sanity target. Treat NFR-01 as the RL gate. Do not derive one from the other.

### LLM latency makes model agents unsuitable for ordinary interactive play unless bounded

`docs/VISION.md`, section 8, records that local models may require 40 to 50 seconds per decision and a game may have roughly 64 decisions. That can produce an hour-long game. The plan acknowledges this but still labels model agents as MVP browser opponents in FR-39.

**Required change:** Define an interactive latency budget. For example:

- model agent may be used only for asynchronous “take turn” play when median decision latency exceeds 5 seconds;
- scripted or learned agents are the default real-time opponent;
- model agents have an explicit maximum turn budget and fall back when exceeded;
- each run records timeout and fallback causes separately.

## Acceptance Criteria and Gates

### The criteria are more measurable than average, but several measure the wrong thing

1. **TC-01 is insufficient for rules fidelity.**  
   One case per rule ID measures catalog coverage, not behavioral correctness.

2. **BC-01 has an undefined threshold.**  
   `docs/SUCCESS_CRITERIA.md`, BC-01 requires “1 complete game, no rule error.” “No rule error” has no oracle. A complete game can be consistently wrong.

3. **TC-16 imposes an unsupported model target.**  
   A local 14B to 32B model must have fallback rate below 20 percent. The research itself, section 8.2, reports high rule-violation rates and admits OQ-R4 is unresolved. This is a hypothesis, not an acceptance threshold supported by project evidence.

4. **TC-18 can be satisfied by a deliberately weak scripted bot.**  
   “More than 50 percent” against the weakest scripted agent is not a meaningful learned-agent quality bar unless that bot is versioned, independently defined, and nontrivial.

5. **TC-20 makes the MVP dependent on five paid external vendors.**  
   A public “MVP complete” condition requiring real calls to five SaaS providers creates avoidable cost, account, outage, region, policy, and API-change dependencies. It does not validate gameplay.

6. **The binding clause is overbroad.**  
   `docs/SUCCESS_CRITERIA.md`, section 4 and `docs/REQUIREMENTS.md`, TR-10 say no version is complete until every real external service returns data. This means an engine or browser milestone cannot be complete during a provider outage, a missing account, a billing issue, or a vendor API retirement. External-service testing is required for external-service features, not for all project completion claims.

### Recommended acceptance gates

- **Rules gate:** conformance corpus reviewed against primary rules and Q-and-A sources. Include branch and interaction coverage, not just rule IDs.
- **Scenario gate:** each public scenario has either an original board license, a private-only reference-board label, or an explicitly generated-remix identity.
- **Determinism gate:** replay all command logs across Windows and Linux with frozen data versions.
- **Secrecy gate:** automated tests prove that each player’s outbound state contains no opponent-hidden entities, identifiers, position data, or logs.
- **Performance gate:** benchmark specification is frozen before implementation optimization begins.
- **Learning gate:** 1 million and 10 million-step pilots demonstrate learning signals before a 100 million-step commitment.
- **Provider gate:** one local endpoint and one selected SaaS provider pass real integration tests before claiming model-agent support.
- **Release gate:** legal content audit and title review occur only for a release candidate, not as a blocker for headless engine work.

## Design Risks That Need Better Framing

### The project does not trace every original ask to a requirement and test

`tasks/discovery_notes.md`, section 4, defines EA-1 through EA-8. `docs/REQUIREMENTS.md`, appendix A summarizes requirement clusters but does not map each EA item to specific FR, NFR, and TC IDs.

The missing traceability is material:

| Original ask | Current coverage | Gap |
|---|---|---|
| Find all possible pieces, maps, rules, scenarios | Research report and discovery notes | No acceptance criterion for completeness, source quality, missing artifacts, or base-game boundary |
| Browser-based version | FR-30 through FR-36 | Offline browser requirement contradicts Python-first architecture |
| Maps that look like boardgame maps | FR-25, FR-26, FR-30, TC-14 | Legal-safe originality standard not defined |
| Tiles/counters that look like boardgame tiles | FR-31, TC-14 only partly | No dedicated counter-art originality, readability, or licensing acceptance test |
| Human-versus-human | FR-37, FR-38 | LAN secrecy and authentication architecture incomplete |
| Human-versus-computer | FR-39 | Interactive latency and agent-quality thresholds incomplete |
| Computer-versus-computer | FR-40, FR-58 | Good basic coverage |
| Learning and evolution | FR-50 through FR-55 | PPO is MVP; evolution of bots and prompts is Scale. Original goal is only partially delivered in MVP |
| Local models | FR-45 through FR-49, IR-01 | Hardware/model reference is unresolved in O-01 and O-02 |
| SaaS models | IR-02 through IR-06 | Five-provider MVP scope is excessive and fragile |

### “All possible pieces, maps, rules, and scenarios” remains unaddressed as a bounded deliverable

The original ask in `tasks/discovery_notes.md`, EA-1, asks to find all possible pieces, maps, rules, and scenarios. The project has chosen base game only, which is a valid owner decision. But the research report states that the full RV-1 through RV-8 appendices contain source data and references, while those appendices are not included in the reviewed repository. It also identifies missing data-card content and unresolved terrain disagreement.

The project therefore cannot yet claim a complete research inventory. It can claim a provisional base-game research synthesis with known gaps.

### The architecture assumes a future Rust port is “mechanical”

`docs/VISION.md`, bet 2, says that a Rust port is mechanical because the core has no I/O and a JSON conformance battery. This is not established. Porting a deterministic tactical rules engine changes:

- integer and serialization semantics,
- random-number-generator implementation,
- ordering behavior,
- map/set iteration behavior,
- JSON parsing and numeric representation,
- exception/error semantics,
- concurrency model,
- binding data conversion,
- test fixture interoperability.

A strong conformance corpus makes the port safer. It does not make it mechanical. Plan it as a separate project with its own budget and exit criteria.

## Recommendations by Priority

### P0: Fix before coding

1. **Resolve the Python/browser/offline contradiction.**  
   Recommended option: use a local Python authoritative host for all initial browser play and remove FR-36 from MVP. Browser hot seat is then “no remote server required,” not “no local process required.”  
   Alternative: use Rust/Wasm from day one. This is technically cleaner for browser delivery but conflicts with the fixed Python-first decision.

2. **Write the missing architecture document before implementing any engine code.**  
   It must define command granularity, phase/subphase state, legal-action API, state ownership, player-view projections, browser-host protocol, replay schema, data-versioning, and Python-to-Rust migration boundaries.

3. **Create a rule-scope matrix for Scenario 1, Scenario 2, Scenario 3, 3A, and excluded 3B.**  
   Resolve the research contradiction between “rules 1 to 41” and “rules 1 to 27.” Each scenario must list required rule IDs, optional rules, tables, counter types, terrain types, and unresolved source gaps.

4. **Separate private original scenarios from public generated scenarios.**  
   Define two explicit product modes. Do not make public fidelity claims for historical scenarios running on non-historical generated maps.

5. **Define player-view projection as a first-class security and architecture requirement.**  
   Add requirements and tests for authoritative state versus per-player visible state. This must cover LAN transport, browser caches, prompts, logs, replays, and debugging tools.

6. **Replace one-case-per-rule acceptance with a behavior and interaction conformance strategy.**  
   No rule engine implementation should start until the project has a conformance-case format, primary-source citation policy, adjudication process, and minimum interaction matrix.

7. **Correct the GPL requirement and legal assertions.**  
   Remove the inaccurate claim that GPL-3 imposes network-source disclosure solely for served JavaScript. Retain a source-link and notice requirement if desired, but describe it as a distribution and project-policy requirement, not as an invented GPL section 7 duty.

### P1: Do before expanding beyond a headless vertical slice

1. Cut MVP to Scenario 1, one generated board fixture, one scripted agent, headless execution, replay, and rules conformance.
2. Define a frozen throughput benchmark. Specify exactly what is measured as an environment step.
3. Add a 1 million-step and 10 million-step RL feasibility ladder before committing to 100 million steps.
4. Implement one local model endpoint only after headless game execution is stable.
5. Select one SaaS provider only after the model-agent harness proves useful locally.
6. Define the LAN threat model honestly. Either make it trusted-party convenience only, or add transport, entropy, throttling, replay, and origin protections.
7. Correct DR-06 and add release-artifact scanning beyond `.gitignore`.

### P2: Do before public release

1. Obtain qualified legal review of branding, board style, counter composition, scenario data, screenshots, and generated-output policy.
2. Add a counter-specific originality and readability rubric, not just the board rubric in TC-14.
3. Add content provenance records for every data table, counter statistic, rule interpretation, and art asset.
4. Add cross-platform deterministic test automation, not merely a requirement to run tests on Windows and Linux.
5. Decide whether private reference layouts may be used in local tests and ensure they cannot contaminate commits, CI artifacts, public replays, screenshots, or release archives.

## Bottom Line

The concept is worth building only if it is treated first as a narrowly scoped, deterministic Game Set I rules-engine project, not as a simultaneous browser, LAN, RL, and multi-provider AI platform. The architecture must first resolve the Python-core versus offline-browser contradiction, define secrecy-preserving player views, and establish a real conformance corpus. Starting from the current material unchanged will produce breadth before fidelity, and the likely result is a visually ambitious but unauditable rules implementation that fails at the project’s stated differentiator.
